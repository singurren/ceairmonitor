# 东航 App 抓包手册（Android + ADB）

## 1. 目标

这份手册的唯一目标是：抓到东航 App 中 `趣游卡 -> 查询某日可兑换航班` 的真实请求和响应。

你不需要一开始就理解所有请求，只需要拿到足够样本，用“对比法”定位真正的目标接口。

## 2. 最推荐方案

优先顺序：

1. `HTTP Toolkit + Android 真机 + ADB`
2. `mitmproxy + Android 真机 + ADB`
3. 如果 HTTPS 被证书校验拦住，再考虑 `Frida` 或退回 `UI 自动化`

如果你已经能让手机通过数据线连接电脑，并且已经授权 `adb`，那就优先走第一种，操作量最小。

## 3. 你最终要交给我的内容

每个关键请求都尽量保留这 6 项：

- 请求 URL
- 请求方法
- 请求头
- 请求体
- 响应体
- 你当时在 App 里做了什么操作

最少准备 3 组样本：

1. 进入趣游卡查询页时的首批请求
2. 查询 `上海 -> 深圳` 某个周日
3. 切换到另一个周一，再查一次

如果能再补一组 `SHA` 和 `PVG` 切换样本，会更容易定位机场字段。

## 4. 最短操作路径：HTTP Toolkit

### 4.1 电脑安装

安装 `HTTP Toolkit` 桌面端。

官网：

- <https://httptoolkit.com/>

### 4.2 手机准备

确认以下命令能看到设备：

```bash
adb devices
```

如果能看到你的手机序列号，说明 ADB 已可用。

### 4.3 启动拦截

打开 HTTP Toolkit，选择：

- `Intercept Android device via ADB`

然后按界面提示执行。它通常会自动：

- 配置 Android 代理
- 安装或引导安装证书
- 尝试让指定 App 走代理

如果它让你选择 App，优先选择东航 App。

### 4.4 在手机上做最小化操作

在开始前，先清空 HTTP Toolkit 的请求列表，避免噪音。

然后在东航 App 里做下面这组动作：

1. 冷启动东航 App
2. 进入趣游卡入口
3. 进入“查询可兑换航班”的页面
4. 查询 `上海 -> 深圳`
5. 记录第一次查询的日期，例如 `2026-04-19`
6. 切换到另一个日期，例如 `2026-04-20`
7. 如果支持，切换 `SHA` / `PVG`

每做一步，记一下时间点或顺序。

## 5. 识别目标接口的方法

不要一开始试图看懂所有包。直接用下面的规则筛：

### 5.1 先按关键词筛 URL

优先关注这些关键词：

- `flight`
- `search`
- `query`
- `benefit`
- `rights`
- `coupon`
- `activity`
- `product`
- `exchange`
- `calendar`

如果趣游卡页面是 H5 或 WebView，还要关注：

- `graphql`
- `api`
- `get...list`
- `detail`

### 5.2 再按“操作变化”筛

真正的目标请求通常满足：

1. 你切换日期后，这个请求会再次发出
2. 请求体里某个日期字段变了
3. 响应里航班列表、日期状态、可兑状态也变了

这三个条件同时满足时，命中率很高。

### 5.3 响应里重点找这些字段

字段名不一定完全一样，但你要重点搜：

- 航班号，如 `MU5375`
- 起飞日期
- 起飞时间
- 出发机场
- 到达机场
- 税费
- 是否可兑换
- 余位 / 名额 / 库存
- 日历可选状态

## 6. 推荐抓样本方式：对比法

这个方法最有效。

### 样本 A

- 路线：`上海 -> 深圳`
- 日期：`2026-04-19`

### 样本 B

- 路线：`上海 -> 深圳`
- 日期：`2026-04-20`

### 样本 C

- 路线：`上海 -> 深圳`
- 日期：`2026-04-21` 或切换 `SHA/PVG`

对比时重点看：

- 哪个请求的 body 里日期变了
- 哪个请求的 response 里航班列表跟着变了
- 哪个请求每次切日期都会稳定出现

如果只找到一个满足这三点的请求，基本就是目标接口。

## 7. 哪些字段必须保留

即使你觉得“不敏感”，也先完整保留：

- `Authorization`
- `Cookie`
- `token`
- `sessionId`
- `deviceId`
- `sign`
- `nonce`
- `timestamp`
- `x-*` 自定义头
- App 版本号
- 渠道号
- 产品 ID / 活动 ID / 页面 ID

原因很简单：这些字段未必是隐私，但可能是复现请求的必要条件。

## 8. 哪些请求可以先忽略

优先忽略这些明显无关的内容：

- 图片
- 字体
- 静态 CSS
- 广告
- 埋点
- 用户中心
- 消息中心
- 首页推荐流

如果请求返回的是纯静态资源，一般先跳过。

## 9. 我建议你记录成这个格式

```text
步骤：
1. 打开东航 App
2. 进入趣游卡
3. 查询 上海 -> 深圳，日期 2026-04-19

可疑请求 1：
POST https://example.com/...
请求头：...
请求体：...
响应体：...

判断：
切到 2026-04-20 后，这个请求再次出现，body 中 date 变为 2026-04-20，
响应中的航班列表也变化，因此怀疑这是目标查询接口。
```

## 10. 如果 HTTP Toolkit 抓不到

常见原因有两类。

### 10.1 App 没走系统代理

表现：

- 浏览器能被抓到
- 东航 App 没有请求或请求很少

处理：

- 用 HTTP Toolkit 的 Android ADB 模式重新注入
- 确认拦截的是目标 App
- 冷启动 App 再试一次

### 10.2 HTTPS 证书校验失败

表现：

- 能看到请求，但失败
- 或者请求直接中断
- 或者提示 SSL、handshake、certificate 相关错误

处理：

1. 先确认证书是否正确安装
2. 再试一次冷启动
3. 如果仍失败，说明可能有 certificate pinning

这时有两个方向：

- 方向 A：用 Frida 绕过 pinning
- 方向 B：放弃接口抓包，改做 UI 自动化

## 11. 如果要升级到 Frida

只有在 HTTP Toolkit / mitmproxy 明显被 HTTPS pinning 卡住时，才需要 Frida。

你需要：

- Android 真机或模拟器
- `adb`
- `frida-tools`
- 可注入的目标环境

但这一步复杂度明显上升，不建议在第一轮就做。

## 12. 用 mitmproxy 的替代路线

如果你更习惯命令行，也可以用 `mitmproxy`。

### 12.1 安装

```bash
pip install mitmproxy
```

### 12.2 启动

```bash
mitmweb -p 8080
```

然后在手机 Wi-Fi 代理中指向你的电脑 IP 和 `8080` 端口，再在手机浏览器打开：

- `http://mitm.it`

安装证书后再打开东航 App。

这条路线也能用，但人工步骤更多，ADB 联动不如 HTTP Toolkit 省事。

## 13. 最关键的判断标准

你最终不是要证明“我抓到了很多请求”，而是要证明：

1. 某个请求和“切换日期 / 查询路线”强相关
2. 这个请求返回了可用于监控的真实业务数据
3. 这个请求可以稳定重复出现

只要这三点成立，我们就能把现在的原型升级成真实监控器。

## 14. 给你的执行建议

第一次抓包时，不要追求完整，按这个顺序来：

1. 先用 HTTP Toolkit 跑通基础拦截
2. 只做 `上海 -> 深圳` 两个日期的对比查询
3. 找出 1 到 3 个可疑请求
4. 把这些请求的完整信息给我
5. 我来帮你判断哪个才是真正的目标接口

- 原始请求/响应导出
