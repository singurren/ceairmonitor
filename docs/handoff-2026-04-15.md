# 东航趣游卡监控项目交接记录

更新时间：`2026-04-17`

## 1. 项目目标

当前项目的长期目标不是泛化的“日期级放票提醒”，而是精确到目标航班时间段的监控。

用户最终目标：

- 去程：`上海 -> 深圳`
- 关注时间：`周一`
- 起飞时间窗口：`07:30 - 09:30`

- 返程：`深圳 -> 上海`
  - `周四 16:00` 以后起飞都可以
  - `周五 12:00` 以后起飞都可以

这意味着最终通知条件应当是：

1. 某个日期可兑换
2. 该日期下存在目标方向
3. 该方向下存在落在目标时间窗口内的航班
4. 若出现新的符合条件航班，应推送通知

这里需要再次强调：

- 只做“日期级可兑提醒”是不够的
- 日期级最多只能作为一级触发器
- 最终报警依据必须是“航班级命中目标时间窗口”

原因是：

- 某一天第一次放票时，未必有用户真正想要的时间段
- 同一天后续仍可能新增新的目标航班
- 如果系统只按“这个日期已经提醒过一次”去重，就会漏掉后续真正有价值的新航班

因此最终事件主键必须落到航班级，而不是只落到日期级。

## 4. 当前真正的技术瓶颈

### 4.1 航班级接口已经基本定位

继续逆向“去兑换”后的机票列表页后，已经确认：

- 机票列表页：`https://m.ceair.com/mapp/reserve/flightList`
- 页面会把 `newParam` 还原成 `searchCondition`
- 真正拉航班列表的接口不是之前优先怀疑的 `pricingv2`
- 实际调用的是：
  - `POST https://m.ceair.com/m-base/sale/shoppingv2`

代码中也已经补了这条探测链路。

### 4.2 航班级监控当前被阿里云 WAF 拦截

这是当前最重要的现实边界。

直接对：

- `https://m.ceair.com/m-base/sale/shoppingv2`

发起服务端 HTTP 请求时，返回的不是业务 JSON，而是阿里云 WAF 验证页。

已实际观察到：

- 直接请求会命中 `405 / 验证页`
- 即使先访问真实 `flightList` 页面拿到 cookie，再带 cookie 请求，仍然可能进入验证页

验证页中能提取到：

- `traceid`
- `sceneId`
- `token`

项目中已经把这类情况定义成：

- `flight-level query blocked by aliyun waf`

### 4.3 当前结论

结论不是“航班级接口没找到”，而是：

1. 航班级接口已经找到
2. 纯服务端轮询大概率会被 WAF 拦截
3. 所以航班级监控要么需要：
   - 浏览器态 cookie / 更完整会话
   - 要么需要浏览器自动化

### 4.4 当前新的推进路线

已经决定把产品主路线调整为：

1. 日期级接口继续保留，但只作为一级触发器
2. 一旦日期级显示某天可兑，就由 `Windows` 真实 Chrome + 插件做航班级确认
3. 最终通知依据必须是航班级结果，而不是“某天有票”这一层
4. Playwright 不再作为默认主路线，只保留为插件路线受阻时的备选方案

这个调整的原因很明确：

- 仅按日期持久化会漏掉“同一天后续新增目标时段航班”的情况
- 用户的真实目标是具体时间段的航班，不是笼统的“某天可兑”

- 插件安装本身不是主要问题
- 插件到本地服务的回传链路并非完全不通

最近确认到的两类现象：

1. 最近一次“最后回传结果”出现：
   - `blocked = true`
   - `reason = shoppingv2_non_json`
   - `status = 405`
   - `contentType = text/html`
   - `bodyPreview` 是 405 HTML 页面片段

   这说明该次 `shoppingv2` 返回的是 WAF / 验证页，不是业务 JSON。

2. 最近一次“调试痕迹”出现：
   - `stage = shoppingv2_empty_flights`
   - `payloadSummary.topLevelKeys = ["res"]`
   - `payloadSummary.flightListType = "undefined"`

   随后补充记录到的 `resPreview` 是一段长密文，说明：

   - `res` 不是普通嵌套 JSON
   - `res` 也不是当前插件可直接 `JSON.parse` 的文本
   - 页面里应当还存在一层前端解密或转换逻辑

### 6.5 本轮已经做过的插件探索

这部分必须记录，避免下次重复走同样路径。

截至 `2026-04-17`，已经在插件中做过以下探索：

1. 在内容脚本里增加了 `payloadSummary.resType / resLength / resPreview`
   - 目的：判断 `res` 到底是普通 JSON、嵌套字符串还是密文
   - 结果：确认 `res` 是密文样式字符串

2. 在页面 hook 里增加了对以下运行时出口的拦截：
   - `JSON.parse`
   - `TextDecoder.decode`
   - `CryptoJS.AES.decrypt`

   目的是在页面运行时直接截获“解密后的航班对象”。

   - 这说明页面的真实解密链大概率不走这些已覆盖的通用出口
   - 更可能是自定义解密函数、闭包内私有函数、wasm，或其它未覆盖路径

4. 随后又追加了一条新的兜底路线：
   - 不再只盯 `shoppingv2` 返回体和解密链
   - 直接在内容脚本里监听页面 DOM 变化
   - 尝试从页面最终渲染出来的航班文本中提取：
     - `flight_no`
     - `dep_time`
     - `arr_time`

5. 这条 DOM 兜底路线的目的：
   - 绕开 `shoppingv2.res` 的密文问题
   - 不依赖前端解密函数名
   - 不依赖 DevTools
   - 直接抓“页面真正展示给用户看的航班结果”

6. 在 DOM 兜底之外，又追加了一层页面状态扫描：
   - 在注入页脚本里定时扫描常见全局状态入口
   - 例如：
     - `window.__NEXT_DATA__`
     - `window.__INITIAL_STATE__`
     - `window.__NUXT__`
     - `window.__STORE__`
     - `window.$store`
     - `window.store`
   - 如果这些对象里已经存在航班数组，就直接提取并上报

7. 这条页面状态扫描路线的目的：
   - 不等网络解密链
   - 不等 DOM 文本完全稳定
   - 直接尝试截获“页面状态层已经持有的航班对象”

这一步的意义不是证明 DOM 抓取一定最终可行，而是：

1. 先验证页面最终渲染层是否比网络解密链更容易稳定截获

3. 继续沿当前主路线推进，而不是回退到 Playwright 主导

## 11. 文档约定

当前项目里已有两类核心文档：

- `spec`
  更适合保存稳定的产品目标、架构约定、能力边界
- `handoff`
  更适合保存时间序列的阶段性进展、踩坑、当前配置和下一步动作

目前判断：

- 不建议把两者完全合并

原因：

1. `spec` 应尽量稳定，不应被每天的阶段性细节污染
2. `handoff` 需要持续追加“今天做了什么、卡在哪里、下次从哪接”
3. 两者目标不同，合并后会同时变得冗长而混乱

建议做法：

- 保留 `spec` 和 `handoff` 分离
- `spec` 负责“项目是什么”
- `handoff` 负责“项目现在做到哪”

另外，当前协作里还必须明确遵守下面这条工作流要求：

1. 每做完一步实际代码改动后，先更新相关文档
2. 文档更新完成后，再做 git 提交与推送
3. 不要把“代码已改、文档未补、git 未同步”拆成分离状态拖着走

当前默认顺序应固定为：

1. 代码改动
2. 文档更新
3. git add / commit / push
